# v206: stock OpenEmu high-resolution presentation interface audit

## Evidence from user's OpenEmu-Silicon source (not patched)

1. `OpenEmuKit/Source/MTLGameRenderer.swift`: bitmap mode creates its conversion buffer using `gameCore.bufferSize` and `gameCore.bytesPerRow`, and builds an output texture from `gameCore.screenRect`. Merely creating a private 6x Metal texture does not make that texture available to this renderer.
2. `OpenEmuKit/Source/MTL3DGameRenderer.swift`: Metal2 mode instead uses `gameCore.createMetalTexture(device:)` and obtains `gameCore.metalTexture` for presentation. It avoids the bitmap pixel format conversion path but has distinct frame scheduling and lifecycle concerns. v201 changed to this mode prematurely and produced black-screen/hang symptoms on the user's Mac.
3. `OpenEmuKit/Source/OpenEmuHelperApp.swift`: the filter chain receives `gameCore.screenRect` as its source rectangle and `aspectSize` as its aspect correction, and window screen-size notifications derive from `screenRect.size`.
4. `OpenEmu/GameViewController.swift`: it uses the provided screen size to calculate the game's default/native window size; `aspectSize` corrects aspect ratio but is NOT an independent physical-resolution selector.

## Meaning

The current v205/v206 bitmap interface supplies 400x480 or 800x480 pixels. GPU-downsampling a 2400x2880 or 4800x2880 image before bitmap delivery loses high-resolution pixels, even if it improves antialiasing. v206 separately verifies that **actual full-size Metal textures** can keep those pixels and remain available on the GPU; it does not claim stock OpenEmu displays them.

Next high-risk milestone: design a resilient Metal2 rendering path where the host sees a high-resolution texture with appropriate source rectangle and where OpenEmu's native-size window logic remains correct. That is not yet demonstrated, and a host restriction may prevent it without an app change. No OpenEmu modifications are permitted for this project.

# Castle 147 — Azahar/OpenEmu Vulkan bridge architecture review

## Verdict

Castle 146 proves a *private* Vulkan owner can survive Azahar preflight
`retro_deinit`, then be released before software reinitialization. It does not
prove the bundled Azahar libretro core can produce Vulkan frames. The next
milestone is a real core-to-frontend Vulkan handoff, not another private render.

## Verified source map (line numbers approximate, Castle 146 snapshot)

| Area | Source location | Current behavior |
|---|---|---|
| Environment dispatch | `azcore/AzaharCore/AzaharGameCore.mm` ~748–920 | Hardware interface and negotiation support GETs rejected; preferred renderer NONE; `SET_HW_RENDER` Vulkan request observed then rejected; negotiation SET rejected. |
| Official Vulkan ABI | `azcore/AzaharCore/AzaharOfficialVulkanABI.mm` | ABI v5 interface and v2 negotiation compile/layout checks; staging of live private handles; **no published live interface**. |
| Private Vulkan ownership | `azcore/AzaharCore/AzaharGameCore.mm` ~34031–34040 and ~35388 | Owner stores loader/instance/device/destroy functions; release destroys device then instance, closes loader. |
| Preflight boundary | `azcore/AzaharCore/AzaharGameCore.mm` ~35740–35880 | Core requests observed during preflight; owner retained across deinit, released before software restart. |
| Libretro core dynamic loading | `azcore/AzaharCore/AzaharGameCore.mm` ~35400–35570 | Bundled `azahar_libretro.dylib` loaded, 16 required exports audited; export presence does not prove Vulkan renderer support. |
| Software presentation | `azcore/AzaharCore/AzaharGameCore.mm` `retro_set_video_refresh`, software video callback path | Existing CPU bitmap/video callback is operational. Private Vulkan readback can feed it, but has not received a game-rendered Vulkan image. |

## Required live data path

1. **Frontend lifetime**: OpenEmu wrapper owns VkInstance, selected VkPhysicalDevice,
   VkDevice, graphics VkQueue, and the resources needed for image transfer/presentation.
   Ownership must cover all libretro initialization, frame callbacks, and deinit.
2. **Core hardware request**: Azahar calls `RETRO_ENVIRONMENT_SET_HW_RENDER`
   with `RETRO_HW_CONTEXT_VULKAN`; wrapper validates the complete official callback
   and only accepts if the real Vulkan backend is operational.
3. **Negotiation**: Azahar supplies v2 negotiation callbacks. The frontend must
   honor the actual ABI contract and determine instance/device creation and
   ownership order. Do not assume the existing private owner can simply be
   substituted without checking the core's negotiation sequence.
4. **Publish interface**: `GET_HW_RENDER_INTERFACE` must return a persistent
   `retro_hw_render_interface_vulkan` v5 with valid instance/gpu/device/queue,
   proc addresses, and fully implemented `set_image` and synchronization hooks.
   Do not publish a stack-local or partially filled interface.
5. **Receive real images**: The core calls `set_image` with a borrowed
   `retro_vulkan_image` and semaphores. Record the image view/layout and relevant
   sync information without taking ownership of the core's image/view.
6. **Synchronize**: Handle queue ownership, semaphore waits, layouts, barriers,
   and fence lifetimes before reading/copying image data. `lock_queue`,
   `unlock_queue`, `get_sync_index`, `get_sync_index_mask`, and `wait_sync_index`
   must have correct semantics where required by the core.
7. **Present**: First safe milestone can be synchronized Vulkan image -> staging
   buffer -> CPU OpenEmu video callback (slower, but leverages known working
   presentation). Later optimize to direct GPU-backed OpenEmu presentation.
8. **Shutdown**: Stop core use of shared handles, wait for outstanding GPU work,
   free frontend transfer/presenter resources, destroy VkDevice, then VkInstance.
   No hardware handle survives owner destruction.

## The central missing components

- A core-facing Vulkan state machine spanning hardware request, negotiation,
  interface publication, image submission, and teardown.
- A complete persistent interface object (v5), not just successful ABI checks.
- A synchronized `set_image` receiver and real frame transfer.
- Proof that the *bundled prebuilt* `azahar_libretro.dylib` actually enters
  hardware Vulkan mode and produces a nonzero number of game images.
- A tested fallback policy when any required feature is missing.

## Minimal implementation order / acceptance gates

**Castle 148 — Negotiation and callback contract instrumentation**
- Instrument the real core's callback sequence and hardware callback fields
  using the official ABI translation unit; keep `SET_HW_RENDER` rejected.
- Identify which frontend callbacks the actual binary requests and whether
  it calls the negotiation SET before/after stage 1 acceptance.
- Capture explicit pass/fail evidence; do not claim a GPU frame.

**Castle 149+ — Persistent frontend interface with fail-closed guard**
- Build a single owner/state object and complete ABI callbacks; test callbacks
  privately, then publish only when image/sync/presenter path is real.
- If the core cannot negotiate with the frontend-owned instance/device,
  revise ownership according to the actual ABI rather than fabricating handles.

**First hardware frame — Acceptance criteria**
- Actual Azahar `SET_HW_RENDER` returns true, core negotiation succeeds,
  `GET_HW_RENDER_INTERFACE` supplies a valid persistent v5 interface,
  real Azahar `set_image` callback count > 0, synchronization passes,
  and the *game-generated* image appears in OpenEmu.
- Log separate counters for private GPU tests and Azahar-origin frames.
- No fake GPU handles, silent software-only success, or dangling callbacks.

## Risk register

1. **Core capability unknown**: export audit alone cannot establish that the
   bundled binary supports the Vulkan renderer. Inspect the binary/source
   configuration and prove behavior with live callbacks.
2. **Handshake ordering**: accepting stage 1 prematurely can make the core
   invoke missing negotiation and crash. Fail closed until complete.
3. **Lifetime**: private owner currently is explicitly released before
   software reinit; a real shared owner needs a different, audited lifetime.
4. **Synchronization**: treating `set_image` as a ready-to-read bitmap risks
   races, undefined layouts, corruption, and device loss.
5. **OpenEmu display**: Vulkan rendering is not complete until a real frame
   reaches the OpenEmu callback/presenter, not merely an offscreen test.

## Scope and limitations

This is a source review and concrete implementation plan, not a working
hardware bridge. No source code changes from Castle 146. No Xcode build or
runtime execution performed here. Earlier private Vulkan PASS messages are
not evidence of Azahar GPU frames.
